AI Agents Read Your Accessibility Tree, Not Your HTML

The data: results dashboard · source repository · raw run data · NVDA run sheet and transcripts

Came here from the talk? What to do next has six steps you can start with tomorrow.

This page is the results record for the experiment. A Spring Boot app serves one flow — register for a workshop — from two sets of templates, with the same controller, validation, stylesheet and data. Only the markup differs, and the session list is asserted pixel-identical by a test.

Both assistive technology and software acting on a user's behalf read the accessibility tree the browser builds from your markup — roles, names and states — rather than your HTML or CSS. So the same markup difference decides whether either one can finish the task.

Who tried it​

Three independent consumers, same task, both variants. Runs made 20 September 2026.

Audited as a Lighthouse accessibility run in Edge DevTools, the broken register form scores 91/100.

None of those findings names the fake dropdown, the role-less Register control or the colour-only error — the three defects that stopped every consumer. For which kind of test does catch which defect, see Test What Scanners Miss.

The four defects, and the fixes​

Each fix is a WCAG requirement, and each one unblocks the screen reader and the agent at the same time.

ProblemBeforeAfterWCAG
"Register" isn't a real link<span onclick="…">Register</span><a href="/register/123">Register</a>2.1.1 Keyboard, 4.1.2 Name, Role, Value
Fields have placeholders, not labels<input placeholder="Full name"><label for="name">Full name</label><input id="name">3.3.2 Labels or Instructions, 1.3.1 Info and Relationships
Fake dropdown<div class="dropdown">Meal preference…</div><select><option>Vegetarian</option></select>4.1.2 Name, Role, Value
Error shown by colour alone<input class="has-error"><div role="alert">Enter a valid email address.</div>3.3.1 Error Identification, 4.1.3 Status Messages

Plus two on the session list: an <img> with no alt, and a page title and main region that are styled <div>s instead of <h1> and <main> (1.1.1, 1.3.1).

How it was measured​

  • Variants. One flow, two template sets, same controller, validation, stylesheet and data. VisualParityTest asserts the session list is pixel-identical. The register form shares the same stylesheet and is not separately screenshot-tested.
  • What the agent can see. Accessibility-tree primitives only — Playwright's ariaSnapshot() to look, role and name lookups to act. Nothing in its toolset reads raw HTML, the DOM or CSS, and it cannot take a screenshot. This isolates the tree as the channel under test.
  • Run order. Five runs per variant per provider, alternating A-B-B-A so neither variant benefits from going first or last.
  • Tool-call cap. 40. The highest run in this data used 34, so no published run was cut off.
  • Excluded data. An earlier pass capped tool calls at 15. All five of Grok's /inaccessible runs hit that cap, which makes their counts the cap rather than a measurement, so they are excluded as spoiled and kept in results/ flagged budgetExhausted rather than deleted. Raising the cap to 40 gave the broken variant more room, not less.
  • Costs are computed, not observed on an invoice, from the rates each vendor published as of 20 September 2026, the day of the runs: $2.00 per million input tokens and $6.00 output for grok-4.6, $2.00 input and $10.00 output for claude-sonnet-5. They also depend on how long a model keeps trying before giving up. Treat them as an order of magnitude at that date.
  • Provenance. Every figure on this page is derived from committed artefacts by a script: the screen-reader counts from the transcripts, the agent figures from one JSON file per run.

To run it yourself, or to regenerate the dashboard, see the repository README. It needs JDK 25 and nothing else; the agent runs on your own API key.

What other people measured​

This experiment tests one small application, so it can show that the problem is real but not how common it is. Published research has measured related questions at larger scale — including a study in which one off-screen <span> took agent click-through on a visually identical advert from 0 of 10 tries to 9 or 10 of 10 across three models. Those papers, what each one found, and where they disagree are summarised on the results dashboard.

What to do next​

You don't need a big project to start. What to Do Next walks you through six short steps on one flow of your own app: look at the accessibility tree, use only the keyboard, listen with a screen reader, find controls by role in your tests, keep a scanner in CI, and learn the WCAG rules behind each fix.

To see which kind of test catches which defect, read Test What Scanners Miss.
