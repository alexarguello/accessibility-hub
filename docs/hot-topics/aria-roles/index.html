ARIA Roles

ARIA (Accessible Rich Internet Applications) is a set of HTML attributes that change what the browser puts in the accessibility tree. Screen readers, voice control software and AI agents read that tree to understand the page. They don't read your CSS.

A role tells them what an element is: a button, a tab, a dialog, an alert. Together with a name ("Save") and a state (pressed, expanded, checked), it's all they know about a control. See AI Agents Read Your Accessibility Tree for what happens when these are missing.

The first rule: use native HTML​

The first rule of ARIA is: if a native HTML element already does what you need, use it instead of adding a role.

<!-- Native: role, name, focus, Enter and Space all work, with zero JavaScript -->
<button type="button">Save</button>

<!-- ARIA: you now have to add all of that yourself -->
<div role="button" tabindex="0" onclick="save()" onkeydown="handleKeys(event)">Save</div>

ARIA changes what the element is called, not what it does. role="button" makes a screen reader say "button". It does not make the element focusable, and it does not make Enter or Space work. Every behavior the native element gives you, you have to write and test yourself.

That's why WebAIM's yearly scan of the top million home pages keeps finding that pages using ARIA have more detected errors on average, not fewer. Use less of it, but use it correctly.

Roles you get for free​

These native elements already have the right role in the accessibility tree:

You writeRole in the treeFree behavior
<button>buttonFocus, Enter, Space
<a href="...">linkFocus, Enter, listed in "Links" by screen readers
<input type="text">textboxFocus, typing, label connection
<input type="checkbox">checkboxFocus, Space, checked state
<select>combobox or listboxFocus, arrow keys, selected state
<h1> … <h6>heading (with level)Heading navigation (H key in NVDA)
<ul>, <ol>list"List, 5 items"
<table> with <th>table, columnheaderTable navigation, headers read with each cell
<nav>, <main>, <header>, <footer>, <aside>navigation, main, banner, contentinfo, complementaryLandmark navigation (D key in NVDA)
<dialog> with showModal()dialogFocus moved inside, Esc to close, rest of page blocked
<details> / <summary>group / disclosure controlExpand and collapse with Enter or Space, expanded state

Adding the same role again (<button role="button">, <nav role="navigation">) does nothing. It just adds noise to the code.

When you do need ARIA​

Use ARIA when HTML has no element for the pattern, or to expose a state HTML can't express:

NeedARIANotes
Tabsrole="tablist", role="tab", role="tabpanel", aria-selectedArrow keys move between tabs. See the APG Tabs pattern.
Announce a change without moving focusrole="status" (polite) or role="alert" (urgent)The element must be in the page before the text changes.
A toggle that opens somethingaria-expanded="true" / "false" on the button, aria-controlsUpdate it every time the state changes.
A toggle buttonaria-pressed="true" / "false"For buttons like "Bold" or a filter.
The current page in navigationaria-current="page"Sighted users see it highlighted; this says it out loud.
An icon-only buttonaria-label="Close"Or visually hidden text inside the button.
A field with help or error textaria-describedby="id-of-text", aria-invalid="true"The text is read after the label.
Hide decoration from screen readersaria-hidden="true"Never on something that can get focus.

Before you build any custom widget, look it up in the ARIA Authoring Practices Guide (APG). It lists the roles, states and keyboard behavior each pattern needs, with working examples.

Common mistakes​

MistakeWhy it breaksFix
<div role="button"> without tabindex="0" and key handlersAnnounced as a button, but keyboard users can't reach or press itUse <button>
aria-label on a <div> or <span> with no roleMany screen readers ignore names on elements with no roleAdd a proper role, or use a real control
aria-hidden="true" on a focusable elementKeyboard focus lands on something the screen reader says doesn't existRemove it, or also make the element unfocusable (inert, or remove from the Tab order)
aria-label that differs from the visible textVoice control users say "click Send", but the control is named "Submit form"Make the name start with the visible text (WCAG 2.5.3)
role="presentation" or role="none" on a focusable or interactive elementThe browser ignores the change, or the control loses its meaningOnly use it on purely visual elements, such as layout tables
States that are never updatedThe menu is open, but aria-expanded still says falseUpdate ARIA states in the same code that changes the UI
role="menu" for site navigationScreen readers switch to application-menu keyboard mode, which users don't expect on a websiteUse <nav> with a list of links
A live region added to the page at the same time as its messageOften nothing is announcedRender the empty role="status" element first, then put the text in

How to check your ARIA​

  • Look at the accessibility tree in DevTools (Chrome/Edge: Elements → Accessibility; Firefox: Accessibility tab). Each control should have the role, name and state you expect.
  • Run axe-core. It catches invalid roles, missing required attributes and aria-hidden on focusable elements. It can't tell you whether a role is the right one.
  • Use the keyboard. Every element with an interactive role must work without a mouse.
  • Use role-based locators in your tests, so a missing role fails the build. See Test What Scanners Miss.
