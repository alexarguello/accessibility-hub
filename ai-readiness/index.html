Screen readers and AI agents do not see a page the way a sighted person does. Both rely on hidden information that says what each part of the page is and does. When that information is missing, both a screen reader user and an AI agent get stuck in exactly the same way.

Both pages below look the same and do the same thing. The only difference: /accessible has proper labels and structure behind it, and /inaccessible is missing them. Every row tried the exact same task: register for a workshop.

NVDA is free screen-reading software used by blind and low-vision people to browse the web. Grok and Claude are two unrelated AI companies' models, tested separately, so this isn't one AI's quirk.

/accessible

Completed the whole task using only the keyboard. When the email was entered wrong, the screen reader announced the problem right away, without the user needing to search for it.

/inaccessible

Using only the keyboard, the task could not even be started: after the filter box, the Tab key jumps straight past the rest of the page, with no way to reach the Register link. Even with a mouse to get into the form, the meal-preference dropdown could never be operated, and the screen reader never announced why the form kept failing to submit.

One problem, two people it breaks

Four real problems from the broken page, and what each one breaks. This is what "fixing accessibility also helps AI agents" looks like in practice.

What's missingScreen readerAI agent
The "Register" link isn't a real link. It only looks like one. Pressing Tab to move through the page skips right over it. There is no way to even open the registration form. The AI looks for something it can recognize as a button or link named "Register" and finds nothing. One AI guessed the web address instead and got in that way; the other gave up and explained it could not find a way in.
The Name and Email boxes show hint text, but have no real label. The screen reader can read the hint text once, but it disappears the moment typing starts, and there is no permanent label to fall back on. The AI's normal way of finding "the field labeled Email" does not work, because there is no real label, only the same fragile hint text the screen reader also has to rely on.
The meal-preference dropdown isn't a real dropdown. It is just styled to look like one. It cannot be reached with the keyboard at all. Even with a mouse, nothing useful is announced: no sign it is a choice to make, no list of options. The AI tries every reasonable way to select an option, and none of them work. There is simply no way to choose a meal preference.
When something is wrong with the form, the only signal is a red border. Confirmed live: after several failed attempts to submit, nothing was announced explaining what was wrong. The user has no way to know why the form keeps rejecting them. When the AI submits and it fails, it gets no explanation either, just the same page again with no sign of what needs fixing.

Independent confirmation this isn't rigged

We also ran an automated accessibility checker (the same engine behind the Lighthouse accessibility audit built into Edge and Chrome DevTools) against both pages, so this isn't just something we're claiming. It only found part of the real problem, though: it can only flag mistakes in code that at least tries to be a real button, field, or link. Code that never tries at all, like the fake dropdown above, is invisible to it. That gap is exactly why testing with a real screen reader and real AI agents still matters, which is what the rest of this page is about.

Of those four, the scan flagged only the labels, and only partly. A high score is not a tested page.

Why it costs more when it fails

Same task, same AI, only the page's markup is different. Every gap in cost and success below comes from that one difference.

A "call" is one action the AI took, like reading the page or clicking something. "Tokens" are roughly how much text the AI had to read and write; more tokens means more time and more cost for the same task.

The fixes, and who requires them

None of this is a matter of taste. Every fix below is required or recommended by the Web Content Accessibility Guidelines (WCAG), the standard most accessibility law and policy is built on. This is the "smallest fixes that restore reliability" this whole project is about, and it's what closes every gap shown above. Six fixes are listed: the four on the register form that everything above is measured against, plus two on the session list — the icon with no text alternative, and the page title and main content being styled divs.
